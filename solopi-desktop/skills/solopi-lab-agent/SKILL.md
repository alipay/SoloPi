# 实验室任务编排

Server Superagent 主导需求分析、用户视角测试方案、用例编写与执行、结果分析和经验沉淀。外部入口完整转发原始要求、纠正、链接、附件定位及授权边界到同一 Server 会话，并展示真实进度/结果；不自行设计业务流程或拆成逐工具遥控指令。

## 需求与准备

1. 关联原始请求及来源会话。已有 jobId/taskId 时读取原对象；不要因等待、断连或工具超时重新提交。
2. 明确用户场景、验收标准、授权环境和执行范围。已有用例直接读取当前版本；新需求先形成可审阅方案和用例，代码只帮助选择验证方法，不替代需求验收。
3. 用例、报告和设备查询使用宿主当前提供的通用工具。读取真实资源与占用，不猜设备配对、包版本或用户身份。若部署要求安装包或切换环境等准备，先取得该准备的成功回执；普通测试不要求额外业务登记。
4. 先读取公用 `solopi-lab-task-ops` Skill 确认当前部署合同。提供 `/v1/lab/*` 的 Node Server 使用其原生 HTTP 合同，不要求额外 Python 服务；独立调度客户端才使用 [通用任务合同](references/request-schema.md) 中的 `solopi-lab` 命令。两种服务账本不能混用。没有对应程序、配置或授权就报告具体缺口，不转到其他执行器规避互斥。

## 提交与跟踪

- 一次逻辑请求使用稳定 requestId；相同请求重试沿用它。caseIds 来自当前用例查询；压测轮数或时长由用户明确指定。
- source 仅是可选来源关联，不代表权限，也不要求某个外部平台身份。通知目标也可省略；没有通知配置仍可提交并查询结果。
- 保存调度返回的 id（jobId）。queued 只是入队；task_id 出现才说明执行器已创建任务。记录原服务地址和 jobId/taskId 关联，不能混用不同服务账本。
- 使用原 jobId 查询、停止、读取产物。未知提交先对账，不换 requestId；设备占用只按真实终态及所有者释放，不手改为空闲。
- 长任务使用已配置的完成事件接续；无通知配置时如实交付查询对象，不承诺自动通知、不无限调用模型轮询。

## 结果与复盘

完成事件只用于提醒。回读同一任务的真实终态及报告，分别交付执行结果、产物可用性和通知状态；传输失败不触发测试重跑。提交拒绝不等于用例失败，CLI 成功也不等于业务通过。

按需求验收和本轮证据分析失败，区分用例/数据、执行工具、环境和产品行为；没有证据则标记未确认。报告与证据关联到 Server 原会话，经验记录来源、适用范围及验证状态，不能把推断保存成已证实规则。

外部业务登记、专属包源和结果投递由部署自行提供的独立适配能力承担，不是本 Skill 或通用调度服务的必需依赖。它们的成功与任务成功分别判断，不扩张用户授权。
